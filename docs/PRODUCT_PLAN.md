# QuotaPet 额度宠物 · 产品规划 v0.1

> 住在 macOS 菜单栏里的像素小宠物。**它的精神状态 = 你的 AI 额度状态。**
> 先做 Claude，架构上预留接入更多 AI 的位置。

## 1. 要解决的问题

- **额度是隐形的**：Claude 的 5 小时额度和每周额度要去设置页或 `/usage` 才看得到，经常写到一半突然被限流。
- **不知道什么时候恢复**：被限流后要反复去看还要等多久。
- **多个 AI 各管各的**：Claude、ChatGPT/Codex、Cursor、Gemini……额度规则和查看入口都不一样。

目标用户：重度使用 Claude 订阅（Pro / Max）的开发者和学生，Claude Code 和桌面端混着用，一天会碰到好几次 5 小时窗口。

## 2. 核心体验

| 场景 | 体验 |
|---|---|
| 写代码时瞥一眼 | 菜单栏：宠物表情 + `27%` |
| 想看细节 | 点一下弹出面板：5 小时 / 本周额度、重置倒计时、消耗速度、「照此速度几点用完」、今天用了多少 |
| 快用完了 | 跨过 75% / 90% / 100% 时各提醒一次（可配置，每个窗口周期只提醒一次） |
| 被限流了 | 宠物睡着，菜单栏改显示恢复倒计时 `1h23m`，恢复时提醒「满血复活」 |

**宠物状态**（跟着最紧张的那个窗口走）

| 使用率 | 状态 | 表现 |
|---|---|---|
| < 50% | 元气满满 | 星星眼、头顶星星一闪一闪 |
| 50–75% | 状态不错 | 安静地看着你，隔一会儿眨眨眼 |
| 75–90% | 有点累 | 半睁眼、汗珠往下滑 |
| 90–100% | 快撑不住 | >_<、掉眼泪 |
| ≥ 100% | 睡着了 | 闭眼、Z 往上飘 + 恢复倒计时 |
| 没数据 | 疑惑 | 问号 |

## 3. 设计原则

1. **一眼可读**：菜单栏只放一个数字加一个表情。
2. **隐私优先**：不联网、不读任何登录凭据，只读本机文件（沿用 `usage_lab.py` 的做法）。
3. **不打扰**：只在跨阈值和恢复时提醒。
4. **省电**：靠文件变化（FSEvents）驱动刷新，不轮询网络。

## 4. 数据方案（Claude）

| 数据 | 来源 | 更新频率 | 精度 |
|---|---|---|---|
| 官方 5 小时 % / 每周 % | Claude 桌面端 `~/Library/Application Support/Claude/plan-usage-history.json` | 桌面端运行时每 15 分钟 | 整数，官方值 |
| 两次官方读数之间的增量 | `~/.claude/projects/**/*.jsonl` 里 Claude Code 每个请求的 token | 实时（文件一变就重算） | 按自动学到的换算率折算的估算值 |
| 其他端（网页 / 手机 / 桌面端聊天）用量 | 官方增量减去同一段时间的本机估算，多出门槛以上的部分 | 每次官方读数 | 估算值；本机同时在用时只认明显多出来的部分 |
| 重置时间 | 用活动时间 + 读数跳变推算（每周额度按固定时间重置，看到过一次重置后每 7 天循环）；Claude Code 被限流时用日志里的限流消息 | — | 推算约 ±15 分钟（每周重置取跳变区间里最晚的时刻，桌面端没开的空档会让它偏晚，多看到几次会收窄），限流消息是精确值；每周重置时间可手动指定 |

- 菜单栏显示的数 = 最近一次官方读数 + 之后本机用量的估算，面板里用 `≈` 标出估算部分。
- **换算率自动学习 + 持续记录**：每 15 分钟的区间都存进本机记录（`~/Library/Application Support/QuotaPet/intervals.jsonl`），从全部记录里学「多少美元 ≈ 1%」（美元按 API 价格算，但缓存读按半价），越近的权重越大（半衰期 3 小时）。重启、隔几天不用都不会忘；没有记录时用起始值 $0.27。
- **只有官方读数或限流消息能宣布「用完了」**：官方读数没到 100% 之前，估算值最多显示 99%。Claude Code 被限流时会在日志里写一条带 `quotaLimits` 的消息（哪个额度、几点恢复），这是服务器的原话，读到就直接算用完。
- 网页端和手机端的用量不在本机日志里，要等下一次官方读数（最多 15 分钟）才会体现。读数到了以后，官方增量里本机日志解释不了的部分算作「其他端」用量：面板会标出每个窗口里其他端用了多少，消耗速度和「几点用完」也会算上它。
- 备选方案（暂不做）：用 Claude Code 的登录凭据调官方 usage 接口，能拿到精确值和重置时间，但要读凭据，和原则 2 冲突。以后如果要做，也只做成用户主动开启的选项。

## 5. 版本路线

**v0.1 MVP（本次）**
- 菜单栏宠物：7 种状态动画，彩色 / 单色两种渲染；菜单栏显示百分比，或限流时显示倒计时
- 面板：各额度窗口、重置倒计时、消耗速度与耗尽预测、今日用量
- 实时估算 + 换算率自动学习 + 持续记录 + FSEvents 自动刷新
- 阈值提醒、额度恢复提醒
- 设置：什么时候出现（跟随 Claude / 一直）、菜单栏显示内容、动画、提醒阈值、自动学习、每周重置时间、开机自启
- 演示模式：1 分钟看完宠物的所有状态

**v0.2 打磨**
- 历史曲线（Swift Charts）：每天 / 每周用量、各窗口峰值
- 等 Sonnet / Haiku 的记录多了，用持续记录重新检验「一个换算率」和「思考程度不用单独算」这两个结论
- 更多宠物动作和装扮（比如连续一周没被限流就解锁新装扮）

**v0.3 多 AI**
- 每个 AI 实现一个 `UsageProvider`（代码里已经预留了这个协议）
- 候选：OpenAI Codex（本地会话日志里好像带额度百分比，待验证）、Cursor、Gemini CLI、GitHub Copilot，以及 API 余额类（Anthropic Console / OpenAI）
- 菜单栏可切换显示哪家，或者一家一只宠物

**v1.0 分发**
- 开发者签名 + 公证、Sparkle 自动更新、桌面小组件

## 6. 技术方案

- Swift 6 + AppKit（`NSStatusItem` / `NSPopover`）+ SwiftUI 面板，用 SwiftPM 构建，只要命令行工具，不需要 Xcode
- 架构：`UsageProvider`（数据源）→ `UsageStore`（调度刷新）→ 菜单栏 / 面板 / 通知
- 宠物：原创像素风二次元角色（参考「Claude 娘」风格：橙色长发、星芒花饰）。菜单栏头像 32×32（16pt），面板半身像 64×64（96pt）；在 `design/` 里用 Python 画原型、出预览图，定稿后导出成 Swift 数据
- 逻辑都在 `QuotaPetCore` 里，由 `swift run QuotaPetChecks` 自检（命令行工具里没有 XCTest）

## 7. 开发中的实测发现（2026-09-25）

- 用 36 小时的真实数据逐个区间对比，usage_lab 的系数在**日常 Opus 会话里把用量高估了 2–3 倍**：只用 Opus 的区间里，官方增量 ÷ 估算增量 ≈ 0.24–0.43；混着用 Sonnet / Haiku 的区间接近 1.0。
- 用 18 个 15 分钟区间做回归，按留一法比较预测误差（2026-09-26）：
  | 模型 | 误差（百分点） |
  |---|---|
  | usage_lab 原系数，不拟合 | 13.2 |
  | **所有模型一个系数（额度 ∝ API 价格）** | **3.4**（$0.31 / 1%） |
  | 按模型分 | 3.9 |
  | 思考 token 单独一个系数 | 3.5 |
  | 按 模型 × 思考程度 分 | 5.0 |
- **思考程度（effort）不需要单独算**：纯 Opus xhigh 和纯 Opus max 的区间都是 $0.349 / 1%。effort 的影响全部体现在思考 token 上，而思考 token 按输出计费，已经算进 API 价格了。每周额度也一样，一个系数最好（≈ $2.2–2.5 / 1%）。
- 所以 App 的默认系数改成所有模型 $0.31 / 1%，Fable 也不再用拍脑袋的数。数据主要是 Opus，Sonnet / Haiku 的样本还少，以后数据多了可以再验证一次。
- 加上自动校准后，00:07 的估算是 33%，几分钟后的官方读数是 32%；不校准的话会显示 39%。

**2026-09-26 补充：缓存读要打折，学习要更快，限流消息可以直接用**

- 长对话里估算会系统性偏高，新的官方读数来了数字会往回跳：上下文越长，缓存读占的成本越大，按 API 原价算出来的换算率会一路漂高。
- 缓存读在额度里大约只算 API 价格的一半，所以按 0.5 倍计（0.4–0.6 之间结果差不多）。缓存读和上下文长度是一起涨的，数据分不开「缓存读便宜」和「长上下文便宜」，但按缓存读打折对两种情况都管用。
- 学习的半衰期从 2 天改成 3 小时，同一个会话里的变化也跟得上。用 `usage_lab.py backtest` 逐区间回测（每个区间只用它之前的数据学）：5 小时额度的平均误差和数字往回跳的次数都少了一半左右，单个区间的最大误差略有增加；每周额度本来就准，变化不大。起始值按新口径重新算过。样本主要是 Opus，数据多了要再回测一次。
- Claude Code 被限流时，日志里有一条带 `quotaLimits` 的 synthetic 消息，写着限流类型和精确的恢复时间，和桌面端的读数对得上，App 现在直接用它。消息里没有账号信息，所以要和同一窗口的官方读数核对：对不上（多半是 Claude Code 和桌面端登的不是同一个账号）就不用。

**2026-09-26 补充：把看不见的其他端用量显示出来**

- 逐段对比官方增量和本机估算：只用 Claude Code 的时段里，差值都在取整和估算误差以内；在网页、手机上用的时段，官方会明显多涨一截。所以本机有请求时，要多出「2 个点 + 本机估算的 20%」才算其他端用量。这段时间里以及开始前 5 分钟本机都没有请求时，官方涨了就算，这 5 分钟是给服务器计数延迟留的余量。
- 面板上每个窗口标出其他端用了多少；消耗速度和「几点用完」把这部分也算进去。
- 同时在其他端用过的区间，官方涨幅混着两边的用量，不再拿来学换算率。回测显示，5 小时额度的误差和数字往回跳的次数又少了一点。挑这种区间时先用按本机花费加权的中位数（混用的区间多一些也拉不动它），再用学到的换算率反复挑到不再变化，所以和面板上算其他端用的是同一套规则。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| `plan-usage-history.json` 是桌面端内部文件，格式可能会变 | 容错解析；读不到时宠物显示疑惑，并说明原因 |
| 桌面端没运行时没有官方读数 | 继续用本机日志估算，并提示读数已过时 |
| 换算率会随模型和套餐变化 | 从持续记录里自动学习，越近的记录权重越大 |
| 重置时间是推算出来的 | 标注「约」；每周重置时间可以手动指定；被限流时用服务器给的精确时间 |
| 限流消息是 Claude Code 日志里的内部字段，格式可能会变 | 解析不到就退回推算；恢复时间比限流晚一个窗口以上的当成不可信，不用 |
